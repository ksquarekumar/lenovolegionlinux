## Delivery

`legionctl-app` (GPUI) is the only graphical UI and installs with the engines: the PKGBUILD builds it with
`legionctl`, `legionctl-system`, `legionctl-operator`, the GNOME Shell extension and the `.desktop` entry. The app
works only while `legionctl-operator` is running and shows a "start the service" state otherwise.

## Built (2026-10-13, M4 part 1; on branch legionctl/legionctl--app until the cargo-deny decision)

`crates/legionctl-app` on gpui-kit 0.7.0 (GPUI Component; pins `gpui-pre` 0.3.7). Pages: **Now** (glance tiles:
mode and why, CPU and GPU watts, CPU temperature, fans; "Check the power policy" shows the dry-run plan, then
Apply or Discard), **Apps & GPU** (displays and their GPU, the desktop GPU choice with a preview), **Health**
(`doctor`), **Bench** (runs and a 30 s CPU bench). Own title bar; follows the system dark/light choice through the
desktop portal; the page scrolls. `legionctl-app [now|gpu|health|bench]` opens a page (the `.desktop` actions use
it). Operator calls run on the app's tokio runtime, blocked on GPUI's background executor, so only GPUI threads wake
the view. The e2e test (`tests/app.rs`) clicks through a headless GPUI window against the real operator on the
recorded machine. Not built yet: mode cards, Rules (needs the configset layers), Tuning wizard, Windows (M5),
OSD for changes the user did not make in the app (the extension does it), live updates by signals (the app polls
every 2 s).

**Resources** (built 2026-10-15, note 22): each resource with its state, its users and a button for each action;
a click shows the dry run (or the route) with Apply and Discard. `legionctl-app resources` opens it.

**Sensors** (built 2026-10-15, note 16): the Now page shows every sensor of `legionctl sensors` (source, name, value
with its unit, or the state). The TUI shows the same table with key `s`, with the range of each history.

## Progressive disclosure

| Level | Surface | Answers |
| --- | --- | --- |
| 0 | Glance strip in the app, OSD, tray icon | What is the machine doing right now? Power source, mode and why, CPU/GPU watts and temperatures, fan RPM, panel refresh. |
| 1 | Mode cards (Quiet, Balanced, Performance, Max power), live tiles, "needs attention" | Choose behaviour in plain words; see the effect live. No numbers needed. |
| 2 | "Because" chips (Base → On AC → Fn+Q → Game running → Your edits), "What this mode sets" | Why each setting has its value, and which rule set it. Selecting a chip highlights the settings it contributes. |
| 3 | Advanced: limit sliders bounded by firmware min/max, plan preview ("2 changes: sustained 90 → 85 W"), Apply/Discard, raw rule files | Precise control. Every write is previewed as a diff first. |

## Views

- **Now**: mode, why, live tiles, attention list.
- **Rules**: the configset layers in plain language ("When plugged in", "After you press Fn+Q", "While a game
  runs"), each with an on/off switch and its raw file under a disclosure.
- **Apps & GPU**: which GPU drives which display and the desktop, primary-GPU choice (next login), MUX mode
  (restart), and per-program GPU, core class and priority.
- **Tuning**: four-step wizard (check idle → scenarios → run → review), knee chart per scenario, "use this value".
- **Health**: `doctor` findings with severity, including kernel modules and DKMS state.
- **Windows**: hazards with the exact fix, one-time restart into Windows, the installed-Windows VM with its
  prerequisites checklist.

## Interaction rules

- Everything updates live from daemon signals: firmware keys, power source, workload changes, other programs
  touching a setting.
- Every state change the user did not make in the app (Fn+Q, unplugging, a game starting) produces an OSD that
  names the new state and the reason.
- Actions that need a restart or re-login say so before they are taken and offer to do it.
- Copy names things the way a user sees them (the "Sustained CPU limit", not `ppt_pl1_spl`); the raw name appears
  only at level 3.
